Vitest is measured by Witness. A Vitest project now needs nothing installed beyond Vitest itself, and the report comes from the toolkit's own instrumenter rather than the project's.

What changed in the driver. The generated wrapper config adds the Witness Vite plugin, points setupFiles at hooks/witness-vitest.mjs, and drops the entire coverage block: no provider, no reports directory, and no include or exclude globs, because Witness's own patterns already decide what gets instrumented. The run carries WITNESS_WASM_DIR, WITNESS_SOURCE_ROOT, and WITNESS_COVERAGE_DIR beside the two the shared setup already set. The environment check no longer demands a pinned @vitest/coverage-istanbul for plain Vitest, and the "Install Vitest" button no longer installs it. Angular's builder still runs on istanbul, so checkAngularEnvironment keeps its requirement until that runner moves.

Why setupFiles is replaced instead of merged. mergeConfig concatenates arrays, which leaves the project's own setup file first. A project's setup file usually sits under the source root, so it is instrumented, and an instrumented module calls the runtime in its prologue. Merged in second, the Witness hook loaded too late and every test file died on "reading 'file' of undefined". The fixture found that, not a code review.

Why the universe is in this delivery and not a later one. Vite only transforms what something imports, so a source file no test reaches is never seen by the plugin and drops out of the report rather than showing as untested. That is the falsely clean report, the worst failure this product has. witnessUniverse already existed and already served Mocha and Playwright, so the Vitest branch calls it the same way.

Why the report is named by the test file. The first version numbered the per-worker reports with a counter held in the hook. Vitest gives each test file a fresh module registry, so the counter reset every time and every file wrote over the last one. The run passed eleven of eleven and reported zero hits for every file but the last, which is worse than a crash. The name now comes from the test file, and the counters are reset after each write so every report is a delta the driver can sum whether or not the runner isolates.

Why a process id was not enough. Witness named its records by process id alone. Under a threads pool one process serves several workers with separate globals, measured here as one process id and three distinct thread ids, so the records interleaved into one file and the reports overwrote each other. The name now carries Node's threadId beside the pid, which costs the library no knowledge of any runner.

The defect that made all of this visible. The Vite plugin compared a path.resolve result against the module id Vite passes to transform. Vite uses forward slashes on every platform and path.resolve on Windows answers with backslashes, so nothing under the source root ever matched, the plugin instrumented nothing, the run still passed, and every file read as untested. Both sides are normalised now. The plugin's own test never caught it because every id it built went through path.join, so the id and the root shared the host separator and agreed with each other while disagreeing with Vite. The test now feeds a posix-style id as well. The same comparison serves Playwright component tests, so this fix applies to that path too.

The side panel header said the name and the build number twice. It read "DeepTest - Polyglot 1.0.10: DeepTest 1.0.10", because two places were naming the same panel. The container's title comes from package.json and the build stamps it, which is right. The view also set its own title in resolveWebviewView, and VS Code renders the container's title and the view's joined by a colon rather than hiding the view's, so every build printed the product twice. The run-time assignment is gone from both extensions and the build is now the only place either title is set. The note in esbuild.mjs that claimed the view's title is hidden and that neither title can change at run time was wrong on both counts and has been corrected, because that note is what would put the line back.
